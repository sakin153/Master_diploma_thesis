# Bugfix Requirements Document

## Introduction

При запросе "4 стола и 4 стула вокруг каждого стола" система должна разместить ровно 4 стола в сетке 2x2 и по 4 стула вокруг каждого стола (всего 16 стульев). Однако наблюдается недетерминированное поведение: в одних прогонах размещается только 3 стола, в других - 4, но стулья размещаются неправильно (не вокруг столов, а в отдельной сетке или хаотично).

**Корневая причина:** LLM не всегда генерирует полный список объектов в семантическом плане. Когда пользователь запрашивает "4 стола", LLM может вернуть только 3 стола (table_1, table_2, table_3), пропуская table_4. Хотя функция `_ensure_plan_covers_chosen_models` должна добавлять недостающие объекты, проблема должна решаться преимущественно на уровне LLM через улучшение промптов.

**Приоритет решения:** Преимущественно через улучшение LLM промптов и инструкций, минимальные изменения в алгоритмической логике только для критических случаев.

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN пользователь запрашивает "N столов и M стульев вокруг каждого стола" где N >= grid_threshold (4) THEN LLM иногда генерирует семантический план с (N-1) столами вместо N, что приводит к недетерминированному размещению

1.2 WHEN в `chosen_models` содержится N экземпляров объекта с Model="table" (где N=4) THEN промпт для LLM не содержит явной инструкции о необходимости включить все N экземпляров

1.3 WHEN LLM возвращает семантический план с (N-1) столами (например, table_1, table_2, table_3 вместо 4) THEN функция `_ensure_plan_covers_chosen_models` не всегда корректно добавляет недостающий table_4 (но это fallback, основная проблема в LLM промпте)

1.4 WHEN пользователь указывает "стулья вокруг каждого стола" THEN LLM генерирует constraints, которые приводят к размещению стульев в отдельной сетке 4x4 или хаотично, вместо привязки к конкретным столам

1.5 WHEN в `chosen_models` есть 4 стола и 16 стульев (4 вокруг каждого) THEN промпт не содержит явного указания на распределение стульев между столами (4 к table_1, 4 к table_2, и т.д.)

### Expected Behavior (Correct)

2.1 WHEN пользователь запрашивает "N столов и M стульев вокруг каждого стола" где N >= grid_threshold (4) THEN LLM SHALL генерировать семантический план с ровно N столами, и система SHALL детерминированно разместить их в сетке (например, 2x2 для N=4)

2.2 WHEN в `chosen_models` содержится N экземпляров объекта с Model="table" (где N=4) THEN LLM SHALL получить явную инструкцию о необходимости включить все N экземпляров в семантический план

2.3 WHEN LLM генерирует семантический план THEN промпт SHALL явно указывать количество каждого типа объектов из `chosen_models` для предотвращения пропусков

2.4 WHEN пользователь указывает "M стульев вокруг каждого стола" THEN LLM SHALL генерировать constraints типа "beside" или "around" для каждого стула, привязывая их к конкретному столу (table_1, table_2, и т.д.)

2.5 WHEN в `chosen_models` есть N столов и N*M стульев THEN промпт SHALL явно указывать распределение: "M стульев вокруг table_1, M стульев вокруг table_2, ..." для корректного распределения

2.6 IF LLM все же пропускает объекты THEN функция `_ensure_plan_covers_chosen_models` SHALL добавить недостающие экземпляры как fallback механизм (но это не основное решение)

### Unchanged Behavior (Regression Prevention)

3.1 WHEN количество объектов одного типа < grid_threshold (4) THEN система SHALL CONTINUE TO использовать beam search вместо grid arrangement

3.2 WHEN в семантическом плане уже присутствуют все экземпляры из `chosen_models` THEN функция `_ensure_plan_covers_chosen_models` SHALL CONTINUE TO возвращать план без изменений

3.3 WHEN объекты имеют явные positional constraints (beside, face_to, on_top_of) THEN система SHALL CONTINUE TO использовать beam search для соблюдения этих constraints

3.4 WHEN пользователь запрашивает размещение объектов без указания "вокруг" THEN система SHALL CONTINUE TO использовать стандартную логику grid/beam placement

3.5 WHEN функция `_normalize_name` удаляет суффикс `_N` из имени модели THEN она SHALL CONTINUE TO корректно группировать экземпляры одного типа (например, "table_1", "table_2" → "table")
