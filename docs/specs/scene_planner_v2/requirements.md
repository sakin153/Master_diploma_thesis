# Scene Planner v2 — Requirements

## 0. Идея (постановка задачи)

> Расширенное описание исходной концепции от автора

### 0.1 Построение графа сцены

Перед размещением система строит **граф сцены** — формальное представление того,
где и как должны стоять объекты. Граф имеет иерархическую структуру.

#### 0.1.1 Иерархия объектов

Объекты делятся на уровни по степени важности расстановки:

- **Anchor (уровень 0)** — объекты, которые размещаются первыми и задают структуру сцены.
  Как правило, это крупная мебель: столы, диваны, кровати, шкафы.
  Anchor является точкой отсчёта для всех зависящих от него объектов.

- **Зависимые объекты (уровень 1+)** — объекты, которые размещаются относительно
  уже расставленных. Каждый такой объект жёстко привязан к конкретному родителю.

Иерархия может быть многоуровневой:

```
стол (anchor, уровень 0)
  └── тарелка (уровень 1, на поверхности стола)
        └── банан (уровень 2, на поверхности тарелки)
```

Это означает: сначала ставим стол → потом тарелку относительно стола → потом банан относительно тарелки.
Не нужно знать абсолютную позицию банана — достаточно знать как он связан с тарелкой.

#### 0.1.2 Группы объектов

**Группа** — это все объекты, привязанные к одному родительскому объекту.
Группа не ограничена одним типом: в одну группу могут входить разнородные объекты,
главное — что все они зависят от одного родителя.

```
стол (anchor)
  └── группа стола:
        ├── 4 стула    ← тип "мебель", вокруг стола
        ├── 4 тарелки  ← тип "посуда", на поверхности стола
        └── 1 лампа    ← тип "освещение", на краю стола
```

Внутри группы объекты размещаются **в порядке зависимостей**: если тарелка должна стоять
"напротив стула", сначала ставятся стулья, затем тарелки с учётом их позиций.

Одинаковые объекты внутри группы **батчуются** для эффективности: LLM получает
один запрос на все 4 стула вместо 4 отдельных. Если таких объектов > 6 — суб-батчи по ≤ 6.

#### 0.1.3 Связи в графе

Каждое ребро графа описывает **отношение** между объектом и его родителем:
- **Позиционное**: на каком расстоянии и в каком направлении
- **Ориентационное**: куда должен смотреть объект относительно родителя
- **Поверхностное**: объект стоит на поверхности родителя (тарелка на столе)
- **Топологическое**: объект рядом с родителем (кресло рядом с диваном)

#### 0.1.4 Граф строится за несколько LLM-запросов

Построение графа разбито на 2–3 отдельных запроса, чтобы не перегружать контекст:

1. **Запрос 1**: определить иерархию объектов и группы
2. **Запрос 2**: описать связи между anchor-объектами (если их несколько)
3. **Запрос 3** (опционально): детализировать сложные под-группы при необходимости

### 0.2 Иерархическое размещение объектов

После построения графа система последовательно размещает объекты, строго следуя иерархии.

#### 0.2.1 Порядок размещения

1. Сначала размещаются все объекты уровня 0 (anchors).
2. Затем — объекты уровня 1 (зависящие от anchors).
3. Затем — уровень 2, и так далее.

Объекты следующего уровня не начинают размещаться, пока не завершён текущий.

#### 0.2.2 Контекст «будущих объектов»

При размещении любого объекта LLM **знает**, что ещё предстоит поставить.
Это критически важно: при размещении стола LLM должна понимать, что вокруг него
будет 4 стула — и оставить достаточно места, а не прижать стол к стене.

```
Разместить: Dining Table (1.5 × 0.9м)

В сцене ТАКЖЕ БУДУТ следующие объекты:
  - 4 × Dining Chair (0.55 × 0.55м) — будут вокруг стола
  - 4 × Plate (0.28 × 0.28м) — будут на столе
  - 1 × Sofa (2.1 × 0.9м) — будет напротив
```

#### 0.2.3 Итеративное размещение с обновлением состояния мира

После каждого размещённого объекта (или батча) система обновляет **world_state** —
текущее состояние сцены с позициями всех уже стоящих объектов.

Каждый следующий LLM-запрос на размещение получает актуальный world_state:

```
Уже в сцене:
  - Dining Table: pos=(0.0, 0.0), 1.5 × 0.9м
  - Dining Chair №1: pos=(0.0, 1.1), 0.55 × 0.55м
  - Dining Chair №2: pos=(0.0, -1.1), 0.55 × 0.55м

Разместить: Dining Chair №3
```

Благодаря этому LLM при размещении стула №3 видит, где стоят стулья №1 и №2,
и не ставит их в одно место.

### 0.3 Примеры (иллюстрация идеи)

#### Пример 1: Гостиная — диван, стол, 4 стула, 4 тарелки, 4 яблока

**Граф сцены:**
```
диван (anchor, уровень 0) — у стены
стол  (anchor, уровень 0) — в 2м перед диваном
  │
  └── группа стола (уровень 1):
        ├── 4 стула    (around стол, смотрят внутрь)
        └── 4 тарелки  (on_surface стол, НО зависят от стульев)
              │         ↑ поэтому внутри группы ставятся ПОСЛЕ стульев
              └── группа тарелки_N (уровень 2, привязана к конкретной тарелке):
                    └── 1 яблоко   (on_surface тарелка_N)
```

**Ключевой момент**: тарелки и стулья — оба уровень 1 (оба зависят от стола как родителя),
но **внутри группы стола** тарелки размещаются после стульев, потому что используют
позиции стульев как ориентир ("напротив каждого стула").

**Порядок размещения:**
1. Диван → LLM знает о столе, стульях, тарелках (оставить место)
2. Стол → LLM знает что вокруг будут стулья (оставить 0.6м зазор)
3. 4 стула → батч, группа стола, шаг 1
4. 4 тарелки → батч, группа стола, шаг 2 (world_state уже содержит стулья)
5. 4 яблока → батч, по одному на каждую тарелку (уровень 2)

---

#### Пример 2: Офис — 6 столов по 4 стула

**Граф сцены:**
```
стол_1 (anchor, уровень 0)  ─┐
стол_2 (anchor, уровень 0)   │← 6 столов размещаются с учётом
стол_3 (anchor, уровень 0)   │  места для стульев вокруг
...                         ─┘
стол_1 → группа: 4 стула   (уровень 1)
стол_2 → группа: 4 стула   (уровень 1)
...
```

**Особенности:**
- При размещении 6 столов LLM знает, что у каждого будет 4 стула → расстояние между столами ≥ 1.5м
- Стулья для стола_1 ставятся до начала работы со столом_2 (каждая группа привязана к своему anchor)
- Внутри группы стулья ставятся итеративно (если группа ≤ 6 — один батч, иначе суб-батчи)

---

### 0.4 Ключевые принципы

| Принцип | Описание |
|---|---|
| **Граф до размещения** | Сначала строим граф, потом ставим — не всё за один LLM вызов |
| **Топологический порядок** | Нельзя разместить зависимый объект раньше его родителя |
| **Живой world_state** | LLM всегда видит актуальную сцену, а не «план» |
| **Контекст будущего** | LLM знает что ещё придёт → умнее занимает пространство |
| **Группы = одинаковые объекты** | Не 4 отдельных стула, а 1 группа из 4 — с правилом расстановки |
| **Несколько LLM вызовов** | Разгружает контекст → лучше качество на каждом шаге |
| **Итеративность внутри группы** | Каждый следующий объект в группе знает позиции предыдущих |

## 1. Контекст

### 1.1 Текущее состояние

`project/scene_planner.py` (Stage 4) принимает список 3D-моделей и генерирует расстановку
объектов в комнате через LLM + алгоритмическую коррекцию коллизий.

**Ключевые ограничения текущей реализации:**

- LLM генерирует позиции всех объектов за один вызов → теряет контекст при > 8 объектов
- При размещении стола LLM не знает, что вокруг него будет 4 стула → ставит стол близко к стене
- Внутри батча 5 стульев LLM не знает куда уже поставила стул №1 когда ставит стул №2
- Иерархия только 2 уровня: anchor → dependent; `яблоко → тарелка → стол` не работает
- Нет формальной структуры данных для графа сцены — всё неявно в JSON от LLM

### 1.2 Мотивация редизайна

Пользователь формулирует запросы с семантическими отношениями:
- "стол и 4 стула у стола, напротив стола стоят два кресла рядом с друг другом"
- "6 столов, по 4 стула у каждого, на каждом столе тарелка"
- "диван, перед ним кофейный столик, на столике книга и чашка"

Текущая система не надёжно обрабатывает такие запросы при > 6 объектов.

## 2. Функциональные требования

### REQ-01: Фаза построения графа сцены

**Приоритет: High**

Система ДОЛЖНА перед размещением строить формальный граф сцены через отдельные LLM-вызовы.

**REQ-01.1** Граф строится в 2–3 LLM-запроса (не в один), чтобы не перегружать контекст.

**REQ-01.2** Граф ДОЛЖЕН содержать для каждого объекта:
- Уровень иерархии (0 = anchor, 1 = зависит от anchor, 2 = зависит от level-1, ...)
- Ссылку на родительский объект
- Тип связи с родителем: `around`, `on_surface`, `beside`, `facing`, `opposite`, `absolute`
- Расстояние до родителя
- Направление взгляда (facing)
- Принадлежность к группе одинаковых объектов

**REQ-01.3** Граф ДОЛЖЕН поддерживать вложенность ≥ 3 уровней:
```
стол (level 0)
  └── тарелка (level 1, on_surface стол)
        └── яблоко (level 2, on_surface тарелка)
```

**REQ-01.4** Граф ДОЛЖЕН описывать связи между anchor-объектами, если их несколько:
- "диван и стол: стол в 2м перед диваном"
- "стол_1 и стол_2: расположены симметрично"

### REQ-02: Группы одинаковых объектов

**Приоритет: High**

**REQ-02.1** Объекты одного типа с одинаковым родителем ДОЛЖНЫ объединяться в группу.
Пример: 4 стула вокруг одного стола = 1 группа `chair_group_table_1`.

**REQ-02.2** Внутри группы объекты размещаются итеративно (по одному или суб-батчами ≤ 6),
с обновлением world_state после каждого размещения.

**REQ-02.3** Если объектов в группе ≤ 6 — один LLM-вызов на всю группу.
Если > 6 — суб-батчи по ≤ 6 с нарастающим контекстом.

### REQ-03: Итеративное размещение с world_state

**Приоритет: High**

**REQ-03.1** После размещения каждого объекта (или батча) система ДОЛЖНА обновлять
`world_state` — структуру с позициями и размерами уже размещённых объектов.

**REQ-03.2** Каждый LLM-вызов размещения ДОЛЖЕН получать `world_state` как часть промпта.

**REQ-03.3** Каждый LLM-вызов размещения ДОЛЖЕН получать описание оставшихся объектов
("в сцене ещё будет: 4 стула (0.55×0.55м), 1 лампа (0.3×1.5м)").

### REQ-04: Контекст будущих объектов при размещении anchors

**Приоритет: High**

**REQ-04.1** При размещении anchor-объекта LLM ДОЛЖНА получать список всех объектов,
которые будут размещены после него, с их размерами.

**REQ-04.2** Это позволяет LLM оставлять достаточно места вокруг стола для стульев.

### REQ-05: Иерархическое размещение уровень за уровнем

**Приоритет: High**

**REQ-05.1** Система ДОЛЖНА обходить граф в топологическом порядке: сначала level 0,
затем level 1, затем level 2, и т.д.

**REQ-05.2** Объекты level N+1 размещаются только после того, как все объекты level N
получили финальные позиции в world_state.

**REQ-05.3** Для каждого объекта на level > 0, LLM-вызов ДОЛЖЕН получать:
- Позицию и размеры конкретного родительского объекта
- Тип связи из графа
- world_state (уже размещённые объекты)
- Описание оставшихся объектов

### REQ-06: Совместимость с существующим пайплайном

**Приоритет: High**

**REQ-06.1** Функция `generate_placement_plan(models, room_half_size, room_type, query)`
ДОЛЖНА сохранить ту же сигнатуру.

**REQ-06.2** Выходной формат ДОЛЖЕН сохранить ту же структуру:
список словарей с полями `Model`, `Pose`, `yaw_deg`, `size`, `is_static`, `model_loc`, `save_fn`.

**REQ-06.3** Фаза коррекции коллизий (`validate_and_repair_layout`) ДОЛЖНА остаться
без изменений и вызываться в конце.

## 3. Нефункциональные требования

### REQ-NF-01: Число LLM-вызовов

Суммарное число LLM-вызовов на сцену с N объектами:
- Фаза 1 (построение графа): 2–3 вызова, не зависит от N
- Фаза 2 (размещение): O(N/6) вызовов
- Итого для 20 объектов: ≤ 10 LLM-вызовов

Текущая реализация: для 20 объектов делает ≈ 4–5 вызовов, но с деградацией качества.
Новая: больше вызовов, но каждый вызов работает с меньшим контекстом → лучше качество.

### REQ-NF-02: Обработка ошибок LLM

**REQ-NF-02.1** Если LLM вернула невалидный граф → fallback к упрощённому графу
через эвристики (как в текущем `_determine_priorities`).

**REQ-NF-02.2** Если LLM не смогла разместить объект → использовать позицию
по умолчанию (рядом с родителем на safe distance) и продолжать.

**REQ-NF-02.3** Каждый LLM-вызов имеет ≤ 3 попытки с feedback об ошибках.

### REQ-NF-03: Стиль кода

- Нет type annotations (`from __future__ import annotations` запрещено)
- Нет type hints в сигнатурах функций
- Простые имена переменных, читаемый код
- Один файл `project/scene_planner.py`

## 4. Граничные случаи

| Случай | Ожидаемое поведение |
|---|---|
| 1 объект | Граф = 1 anchor, размещается в центре |
| Все объекты одинаковые (10 стульев) | Одна группа, батчи по ≤ 6 |
| Запрос без явных отношений ("5 объектов") | Граф строится эвристически |
| Глубина > 3 уровней | Ограничить до 3 уровней, предупредить |
| Циклическая зависимость в графе | Обнаружить и разорвать цикл |
| LLM строит граф с несуществующим ID | Валидация + retry |
| Очень плотная сцена (density > 0.8) | Ранний переход к LLM fallback (как сейчас) |
