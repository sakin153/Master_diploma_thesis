## Критические Находки

### 1. **Избыточные Повторы LLM в Планировании Сцены**

**Проблема:** Алгоритм размещения делает 30+ вызовов LLM для простой сцены с 13 объектами.

**Корневые Причины:**
- **Жесткие пространственные ограничения:** 5 бананов в маленькой коробке - это сложно
- **Слишком строгая валидация:** LLM с трудом соответствует точным требованиям footprint
- **Нет обучения между повторами:** Каждый повтор начинается с нуля, не учится на предыдущих провалах
- **Эскалация температуры:** Увеличение T до 1.0 делает ответы более случайными, не обязательно лучше

**Доказательства из логов:**

### 2. **Пробел в Системе Логирования**

**Проблема:** Кастомный логгер захватил только 1 вызов LLM, но на самом деле было сделано 37.

**Корневая Причина:** Вызовы LLM внутри `generate_placement_plan()` обходят логгер, потому что используют внутреннюю функцию `_llm_request()` напрямую.

### 3. **Нет Кеширования Промежуточных Результатов**

**Проблема:** Каждый запуск начинается с нуля, даже для идентичных типов объектов.

**Возможности:**
- Классификации физики можно кешировать по типу объекта
- Размеры моделей можно кешировать по UUID
- Успешные паттерны размещения можно кешировать

## Почему Планирование Сцены Занимает Так Долго

### Основная Проблема: LLM-Основанное Пространственное Рассуждение - Это Сложно

**Что должна делать LLM:**
1. Понимать 3D пространственные отношения
2. Уважать размеры объектов и footprint'ы
3. Избегать перекрытий и коллизий
4. Следовать семантическим ограничениям ("в ряд", "внутри коробки")
5. Генерировать точные числовые координаты

**Почему часто проваливается:**
- LLM обучены на тексте, а не на 3D геометрии
- Маленькие числовые ошибки вызывают провалы валидации
- Нет визуальной обратной связи для исправления ошибок
- Каждый повтор независим (нет обучения)

**Каскад Повторов:**
```
Попытка 1 (T=0.7): Бананы перекрываются → ПРОВАЛ
Попытка 2 (T=0.8): Бананы вне коробки → ПРОВАЛ  
Попытка 3 (T=0.9): Бананы слишком близко → ПРОВАЛ
Попытка 4 (T=1.0): Случайное размещение → ПРОВАЛ
Попытка 5 (T=1.0): Случайное размещение → ПРОВАЛ
Попытка 6 (T=1.0): Случайное размещение → ПРОВАЛ
Попытка 7 (T=1.0): Случайное размещение → ПРОВАЛ
Попытка 8 (T=1.0): Удачный успех! → УСПЕХ
```

**Каждая попытка = ~3 секунды = 24 секунды потрачено впустую**

## Сравнение с Другими Подходами

### Текущий: Чистый LLM Подход
- **Плюсы:** Гибкий, обрабатывает сложные семантические ограничения
- **Минусы:** Медленный, ненадежный, дорогой (много API вызовов)
- **Время:** 96 секунд для размещения

### Альтернатива: Гибридный Подход (Рекомендуется)
- **LLM:** Высокоуровневые решения (какие объекты, отношения)
- **Эвристики:** Низкоуровневое размещение (точные координаты)
- **Плюсы:** Быстро, надежно, все еще гибко
- **Минусы:** Требует больше кода
- **Оценочное Время:** 15-20 секунд для размещения

### Альтернатива: Чистый Эвристический Подход
- **Плюсы:** Очень быстро, детерминированно
- **Минусы:** Менее гибко, не может обрабатывать сложную семантику
- **Оценочное Время:** 1-2 секунды для размещения

## Заключение

Pipeline работает, но **серьезно замедлен избыточными повторами LLM в Этапе 4 (Планирование Сцены)**. Корневая причина в том, что LLM с трудом справляются с точным пространственным рассуждением, что приводит к провалам валидации и каскадам повторов.

**Ключевые Метрики:**
- 65% времени тратится на планирование сцены
- 67% вызовов LLM - это повторы
- 96 секунд на то, что должно занимать 15-20 секунд

**Рекомендуемый План Действий:**
1. **Немедленно:** Ослабить ограничения валидации (1 час работы, улучшение на 40%)
2. **Краткосрочно:** Добавить эвристические fallback'и (1 день работы, улучшение на 60%)
3. **Долгосрочно:** Реализовать гибридный LLM+эвристический подход (1 неделя работы, улучшение на 80%)

**Ожидаемый Результат:**
С оптимизациями Приоритета 1, pipeline должен завершаться за **~70 секунд** вместо 148 секунд, с гораздо более надежным размещением и меньшими затратами на API.
