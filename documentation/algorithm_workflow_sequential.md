# ПОСЛЕДОВАТЕЛЬНОЕ ОПИСАНИЕ РАБОТЫ АЛГОРИТМА АВТОМАТИЧЕСКОЙ РАССТАНОВКИ ТРЁХМЕРНЫХ ОБЪЕКТОВ

## 1. ОБЩАЯ АРХИТЕКТУРА АЛГОРИТМА

Разработанный алгоритм представляет собой последовательный конвейер обработки данных, состоящий из шести основных стадий. Каждая стадия принимает на вход результат работы предыдущей стадии, выполняет специфические преобразования и передаёт обработанные данные следующей стадии.

### Таблица 1. Краткая характеристика стадий алгоритма

| Стадия | Название | Входные данные | Выходные данные |
|--------|----------|----------------|-----------------|
| 0 | Расширение запроса | Текстовая строка | SceneSpec |
| 1 | Подбор моделей | SceneSpec | Список моделей |
| 2 | Загрузка и масштабирование | Список моделей | Модели с размерами |
| 2.5 | Классификация физики | Модели с размерами | Модели с физикой |
| 3 | Расчёт размера помещения | Модели с размерами | room_half_size |
| 4 | Планирование расстановки | Модели, размер помещения | Координаты объектов |
| 5 | Сборка MuJoCo XML | Координаты объектов | XML-файл сцены |

## 2. СТАДИЯ 0: РАСШИРЕНИЕ ПОЛЬЗОВАТЕЛЬСКОГО ЗАПРОСА

### 2.1. Назначение стадии

Первая стадия алгоритма предназначена для преобразования краткого неструктурированного текстового описания пользователя в формализованную спецификацию сцены. Данная стадия решает задачу извлечения семантической информации из естественного языка и её структурирования в машиночитаемый формат.

### 2.2. Входные и выходные данные

**Входные данные:** произвольная текстовая строка на естественном языке (русском или английском).

Пример: *"Стол с четырьмя стульями и тарелками на столе"*

**Выходные данные:** объект SceneSpec, содержащий следующие поля:
- `original_query` — исходный запрос пользователя
- `expanded_description` — расширенное текстовое описание сцены
- `estimated_objects` — список объектов с количествами и примечаниями
- `room_half_size` — оценочный размер помещения (половина стороны квадрата)

### 2.3. Последовательность операций

**Шаг 1.** Формирование промпта для большой языковой модели. Система создаёт структурированный промпт, включающий исходный запрос пользователя, инструкции по формату ответа, список допустимых типов помещений и ограничение на максимальное количество объектов (50 экземпляров).

**Шаг 2.** Отправка запроса к БЯМ. Промпт отправляется к языковой модели (по умолчанию deepseek-v3.1:671b-cloud через локальный сервер Ollama) с параметрами:
- temperature = 0.0 (детерминированный режим)
- seed = 42 (фиксированное начальное значение)
- max_tokens = 4000
- timeout = 180 секунд

**Шаг 3.** Получение и парсинг JSON-ответа. БЯМ возвращает структурированный ответ в формате JSON, содержащий все необходимые поля спецификации сцены.

**Шаг 4.** Контроль количества объектов. Вычисляется суммарное количество экземпляров всех объектов. Если сумма превышает 50, применяется пропорциональное масштабирование с сохранением минимум одного экземпляра каждого типа объекта.

**Шаг 5.** Извлечение размера помещения. Из поля `room_dimensions_hint` извлекается числовое значение `room_half_size` посредством регулярных выражений и эвристических правил.

**Шаг 6.** Формирование объекта SceneSpec. Все обработанные данные упаковываются в результирующую структуру данных.

## 3. СТАДИЯ 1: ПОДБОР 3D-МОДЕЛЕЙ ИЗ КАТАЛОГА

### 3.1. Назначение стадии

Вторая стадия алгоритма осуществляет сопоставление абстрактных имён объектов из спецификации сцены с конкретными 3D-моделями из локального каталога. Стадия решает задачу семантического поиска и ранжирования моделей по степени соответствия запросу.

### 3.2. Структура каталога моделей

Каталог представляет собой JSON-файл (assets/manifest.json), содержащий метаданные всех доступных 3D-моделей. Каждая запись каталога имеет следующую структуру:
- `uuid` — уникальный идентификатор модели
- `name` — имя модели
- `categories` — список категорий (например, furniture, seating)
- `tags` — список тегов для поиска
- `file_path` — путь к GLB-файлу модели

### 3.3. Алгоритм ранжирования моделей

Для каждого объекта из списка `estimated_objects` выполняется следующая процедура:

**Этап 1. Токенизация и нормализация.** Имя объекта разбивается на токены (слова), к каждому токену применяется сингуляризация (приведение к единственному числу), все сравнения производятся в нижнем регистре.

**Этап 2. Вычисление скоринга.** Для каждой модели в каталоге вычисляется числовой балл согласно правилам, представленным в таблице 2.

### Таблица 2. Правила вычисления балла соответствия модели

| Критерий | Изменение балла |
|----------|-----------------|
| Точное совпадение имени объекта с именем модели | +20 |
| Частичное вхождение имени объекта в имя модели | +12 |
| Вхождение имени объекта в метаданные модели | +6 |
| Совпадение токена с именем модели | +4 за токен |
| Совпадение токена с метаданными | +2 за токен |
| Совпадение с категорией модели | +5 |
| Модель помечена как abstract/icon/logo/ui | -15 |
| Модель является миниатюрой/игрушкой (если не запрошена) | -10 |
| Инвалидная коляска для запроса "chair" | -12 |
| Лампа/светильник для запроса "desk/table" | -15 |

**Этап 3. Сортировка и отбор кандидатов.** Модели сортируются по убыванию балла, отбираются топ-10 моделей с баллом не менее 3, дубликаты по паре (uuid, name) исключаются.

### 3.4. Уточнение выбора через языковую модель

Если количество кандидатов превышает единицу, система обращается к БЯМ с промптом, содержащим исходный запрос пользователя, имя искомого объекта и список кандидатов с их метаданными. БЯМ возвращает UUID наиболее подходящей модели с обоснованием выбора.

**КРИТИЧЕСКОЕ ИЗМЕНЕНИЕ:** Если БЯМ не смогла выбрать модель (вернула None), система выбрасывает RuntimeError. Fallback на первый ранжированный кандидат УДАЛЁН.

### 3.5. Резервные механизмы

При отсутствии подходящих моделей применяется словарь синонимов, отображающий распространённые имена объектов на имеющиеся в каталоге модели:
- "book" → "box"
- "lamp" → "bottle"
- "pillow" → "cushion"
- "sofa" → "lounge chair"
- "tv" → "television"
- "tv stand" → "table"
- "couch" → "lounge chair"
- "rug" → "carpet"

Если и это не помогает, объект пропускается с выводом предупреждения в лог.

## 4. СТАДИЯ 2: ЗАГРУЗКА И МАСШТАБИРОВАНИЕ МОДЕЛЕЙ

### 4.1. Назначение стадии

Третья стадия алгоритма осуществляет загрузку геометрии выбранных 3D-моделей и вычисление их физических размеров через LLM Batch Autoscaling.

### 4.2. Загрузка геометрии

Для каждой модели из списка выполняется:
1. Чтение GLB-файла с использованием библиотеки trimesh
2. Вычисление ограничивающего параллелепипеда (AABB)
3. Расчёт физических размеров: `size = [max_x - min_x, max_y - min_y, max_z - min_z]`

### 4.3. LLM Batch Autoscaling

Система использует БЯМ для определения реалистичных размеров объектов:

**Шаг 1.** Дедупликация моделей по имени и усреднение геометрии.

**Шаг 2.** Определение единиц измерения через эвристику `_infer_unit_scale()`:
- `max_dim > 100.0` → 0.001 (мм → м)
- `max_dim > 10.0` → 0.01 (см → м)
- `max_dim > 3.5` → 0.1 (дм → м)
- `max_dim < 0.01` → 100.0
- `max_dim < 0.05` → 10.0
- **Fallback**: 1.0 (уже в метрах)

**Шаг 3.** Три независимых запроса к БЯМ с разными параметрами:
- temperature: 0.2, 0.4, 0.6
- seed: 42, 1042, 2042
- timeout: 180 секунд

**Шаг 4.** Агрегация результатов:
- Мода по корзинам 0.05м для каждой оси
- При равенстве мод — медиана всех ответов

**КРИТИЧЕСКОЕ ИЗМЕНЕНИЕ:** Если БЯМ не вернула размеры после 3 попыток, система выбрасывает RuntimeError. Fallback-таблица размеров УДАЛЕНА.

**Шаг 5.** Нормализация масштаба:
- Определение оси высоты (удлинённые объекты, up_axis)
- Масштабирование по длинной оси
- Clamp: ±25% от LLM цели
- Финальный clamp: [1e-4, 1000.0]

Масштабированные размеры сохраняются в поле `size` каждой модели в формате [width_x, height_z, depth_y].

## 5. СТАДИЯ 2.5: КЛАССИФИКАЦИЯ ФИЗИЧЕСКИХ СВОЙСТВ

### 5.1. Назначение стадии

Стадия 2.5 определяет физические свойства объектов (static/dynamic) для корректной работы физического симулятора.

### 5.2. Процесс классификации

**Шаг 1.** Формирование payload для БЯМ с информацией о каждом объекте:
- uuid, name, size_wdh_m
- scene_description, room dimensions

**Шаг 2.** Запрос к БЯМ для классификации всех объектов.

**Шаг 3.** Парсинг ответа и нормализация значений:
- "static"/"статичный" → True
- "dynamic"/"динамичный" → False

**КРИТИЧЕСКОЕ ИЗМЕНЕНИЕ:** Если БЯМ не вернула решение для объекта, система выбрасывает RuntimeError. Heuristic fallback (volume >= 0.1м³) УДАЛЁН.

**Шаг 4.** Volume Guard (применяется ТОЛЬКО к dynamic объектам):
- Если объект классифицирован как dynamic, но `volume >= 0.5м³`
- Принудительно переклассифицируется в static
- Предотвращает "летающую мебель"

## 6. СТАДИЯ 3: РАСЧЁТ РАЗМЕРА ПОМЕЩЕНИЯ

### 6.1. Назначение стадии

Четвёртая стадия алгоритма определяет размер виртуального помещения на основе суммарной площади размещаемых объектов.

### 6.2. Алгоритм вычисления

Вычисление размера помещения выполняется в следующей последовательности:

**Шаг 1.** Вычисление суммарной площади объектов. Для каждой модели вычисляется площадь проекции на пол (footprint = width × depth), умножается на количество экземпляров, результаты суммируются.

**Шаг 2.** Применение фиксированного коэффициента расширения. Используется универсальный коэффициент циркуляции 8.0 для всех типов сцен.

**Шаг 3.** Вычисление базового размера по формуле:

```
room_area = total_footprint × 8.0
base_size = √(room_area) / 2.0
```

**Шаг 4.** Округление. Полученное значение округляется до кратного 0.5 метра:

```
room_half_size = round(base_size × 2) / 2.0
```

**Шаг 5.** Применение ограничений. Результат ограничивается диапазоном [2.5, 25.0], что соответствует помещениям от 5×5 до 50×50 метров.

## 7. СТАДИЯ 4: ПЛАНИРОВАНИЕ РАССТАНОВКИ (ОСНОВНОЙ АЛГОРИТМ)

Данная стадия является наиболее сложной и объёмной частью алгоритма. Она состоит из четырёх последовательных подэтапов, каждый из которых решает специфическую подзадачу планирования расстановки объектов.

### 7.1. ПОДЭТАП 4.1: Построение иерархического графа сцены

#### 7.1.1. Назначение подэтапа

Первый подэтап осуществляет построение ориентированного ациклического графа (DAG), представляющего иерархическую структуру сцены. Узлы графа соответствуют логическим группам одинаковых объектов, рёбра представляют отношения "родитель-потомок".

#### 7.1.2. Структура узла графа

Каждый узел графа содержит следующие поля:
- `node_id` — уникальный идентификатор узла
- `model_name` — имя 3D-модели
- `instances` — количество экземпляров в группе
- `parent_id` — идентификатор родительского узла (null для корневых узлов)
- `relationship` — описание пространственного отношения
- `place_order` — порядок размещения внутри группы
- `depends_on` — идентификатор узла, от которого зависит размещение
- `anchor_hint` — подсказка о привязке к помещению
- `level` — уровень узла в иерархии (вычисляется автоматически)

#### 7.1.3. Типы пространственных отношений

Система поддерживает следующий набор типов отношений.

### Таблица 5. Типы пространственных отношений между объектами

| Тип | Описание | Вычисление Z-координаты |
|-----|----------|-------------------------|
| in_room | Корневой объект в помещении | z = height/2 (на полу) |
| on_surface | Объект на верхней грани родителя | z = parent_top + height/2 + clearance |
| stacked_on | Объект в стопке с другим объектом | Аналогично on_surface |
| in | Объект внутри контейнера | С учётом слоёв |
| around | Кольцевое расположение вокруг родителя | z = height/2 (на полу) |
| beside | Объект рядом с родителем | Наследуется от родителя |
| in_front | Объект перед родителем | Наследуется от родителя |
| behind | Объект позади родителя | Наследуется от родителя |
| facing | Объект обращён к родителю | Наследуется от родителя |

#### 7.1.4. Последовательность построения графа

**Шаг 1.** Формирование промпта для БЯМ. Система создаёт структурированный промпт, содержащий исходный запрос пользователя, размер помещения, список доступных моделей с количествами, контрольную сумму экземпляров и подробные инструкции по формату ответа.

**Шаг 2.** Запрос к БЯМ. Промпт отправляется к языковой модели, которая возвращает массив узлов графа в формате JSON.

**Шаг 3.** Нормализация группировки. Выполняется два прохода:
- а) Слияние узлов типа "around" с одинаковым reference
- б) Слияние узлов с идентичной полной сигнатурой (model_name, parent_id, relationship.type, reference, facing, distance)

После слияний обновляются все ссылки согласно карте замен.

**Шаг 4.** Вычисление уровней узлов. Для каждого узла вычисляется уровень в иерархии по формуле:

```
level = 0, если parent_id = null
level = parent_level + 1, иначе
```

**Шаг 5.** Структурная валидация. Проверяется:
- все ссылочные поля указывают на существующие узлы
- граф не содержит циклов
- все имена моделей валидны
- количество экземпляров в каждом узле ≥ 1

**Шаг 6.** Проверка количеств. Для каждой модели суммируются `instances` всех узлов с данным именем модели и сравниваются с ожидаемым количеством. Несовпадение считается ошибкой.

**Шаг 7.** Обработка ошибок валидации. При неудаче валидации БЯМ получает до 3 попыток с обратной связью (описанием ошибок предыдущей попытки). При исчерпании попыток активируется эвристический построитель графа.

**Шаг 8.** Эвристический построитель (резервный механизм). Использует словари ключевых слов для определения уровней объектов и создаёт граф с простыми отношениями без участия БЯМ.

**Шаг 9.** Раскрытие множественных якорей. Если корневой узел имеет `instances > 1`, он разбивается на отдельные узлы по одному экземпляру, потомки распределяются между ними.

### 7.2. ПОДЭТАП 4.2: Определение отношений между якорями

#### 7.2.1. Условия активации подэтапа

Подэтап выполняется только при наличии нескольких корневых узлов (уровень 0) или корневого узла с количеством экземпляров более одного.

#### 7.2.2. Процесс определения отношений

Система формирует промпт для БЯМ, содержащий информацию о всех корневых узлах с их размерами и будущими потомками. БЯМ определяет, как корневые объекты расположены относительно друг друга: каждый якорь может быть привязан к виртуальному "room_center" или к другому якорю через пространственное отношение.

#### 7.2.3. Топологическая сортировка

На основе полученных отношений строится граф зависимостей и выполняется топологическая сортировка алгоритмом Кана для определения порядка размещения корневых узлов.

### 7.3. ПОДЭТАП 4.3: Определение отношений внутри групп

Для каждого корневого узла, имеющего потомков, система формирует контекст группы и обращается к БЯМ для уточнения отношений между потомками. БЯМ может изменить типы отношений, добавить зависимости между потомками (поле `depends_on`), уточнить порядок размещения (`place_order`) и параметры отношений (distance, facing).

### 7.4. ПОДЭТАП 4.4: Иерархическое размещение объектов

#### 7.4.1. Инициализация состояния мира

Создаётся структура данных `world_state`, содержащая:
- `placed_instances` — список уже размещённых экземпляров объектов
- `remaining_models` — словарь ещё не размещённых моделей
- `room_half_size` — размер помещения

#### 7.4.2. Обход графа по уровням

Размещение выполняется уровень за уровнем, начиная с корневых узлов (уровень 0). Внутри каждого уровня узлы группируются по родителю и сортируются топологически по полю `depends_on`.

#### 7.4.3. Размещение корневого уровня (level = 0)

Для корневых объектов предусмотрены три режима размещения в зависимости от конфигурации:

**Режим 1. Единственный корень в одном экземпляре.** Применяется детерминированное размещение без обращения к БЯМ. Координаты определяются по полю `anchor_hint.region`:
- "center" → (0, 0)
- "near_wall" → (0, room_half_size - 0.6)
- "corner" → (0.7 × room_half_size, 0.7 × room_half_size)

Z-координата вычисляется как height/2 (объект стоит на полу).

**Режим 2. Единственный корень во множестве экземпляров.** Экземпляры разбиваются на батчи по 6 штук. Для каждого батча выполняется запрос к БЯМ. При неудаче применяется fallback: монотонное смещение по оси X с шагом 0.8 метра.

**Режим 3. Несколько различных корневых узлов.** Подготавливается контекст будущих потомков для каждого корня. Выполняется запрос к БЯМ для координированного размещения всех корней. При неудаче применяется fallback: равномерная сетка.

#### 7.4.4. Размещение зависимых уровней (level > 0)

Для зависимых объектов выполняется следующая последовательность операций:

**Этап 1. Группировка и сортировка.** Узлы группируются по `parent_id`, внутри каждой группы выполняется топологическая сортировка по `depends_on` с дополнительной сортировкой по `place_order`.

**Этап 2. Проверка на координированное размещение (coplace).** Если выполняются условия:
- количество узлов-сиблингов ≥ 2
- суммарное количество экземпляров ≤ 8
- все узлы без зависимостей `depends_on`
- все узлы типа on_surface/stacked_on/in

то применяется координированное размещение всей группы одним запросом к БЯМ.

**Этап 3. Размещение единственного экземпляра.** Выполняется в следующей последовательности:
1. Формирование инструкции размещения с информацией о родителе и опорных объектах
2. Запрос к БЯМ (до 6 попыток, с 3-й попытки активируется режим RELAXED FALLBACK)
3. Валидация: проверка границ помещения и попадания в проекцию родителя
4. Детерминированный пересчёт Z-координаты по формуле:

```
z = height/2,                           если relationship.type = "around"
z = parent_top + height/2 + clearance, если parent_id ≠ null
z = height/2,                           иначе
```

5. Дополнительная LLM-валидация позиции (проверка коллизий и согласованности)

**Этап 4. Размещение группы экземпляров.** Процесс включает:
1. Проверку на N:K расщепление (равномерное распределение потомков между родителями)
2. Анализ расслоения для типа "in" (вычисление вместимости слоя, планирование слоёв)
3. Планирование стратегии раскладки для on_surface (паттерн, шаг, отступы)
4. Батч-размещение (батчи по 6 экземпляров, до 5 попыток с увеличением temperature)
5. Валидацию: границы + проекция родителя + минимальный просвет между объектами
6. Fallback: последовательное размещение по одному экземпляру (до 8 попыток каждый)
7. Детерминированный пересчёт Z для всех экземпляров

### Таблица 6. Параметры батч-обработки и валидации

| Параметр | Значение |
|----------|----------|
| Размер батча | 6 экземпляров |
| Количество попыток БЯМ | 6 для одиночных, 5 для батчей |
| Количество попыток в fallback | 8 для последовательного размещения |
| Вертикальный зазор (clearance) | 0.02 метра |
| Коэффициент расслоения (layer spacing) | 1.10 |
| Максимум экземпляров для coplace | 8 |
| Минимум узлов для coplace | 2 |

## 8. СТАДИЯ 5: СБОРКА MUJOCO XML

### 8.1. Назначение стадии

Финальная стадия алгоритма преобразует результаты планирования расстановки в формат XML физического симулятора MuJoCo.

### 8.2. Последовательность формирования XML

**Шаг 1.** Создание корневого элемента `<mujoco>` с указанием версии модели.

**Шаг 2.** Формирование секции `<asset>`. Для каждой уникальной модели добавляются элементы `<mesh>` для визуализации и коллизий, материалы и текстуры.

**Шаг 3.** Формирование секции `<worldbody>`. Добавляются:
- пол (geom type="plane")
- четыре стены
- источники освещения

**Шаг 4.** Добавление размещённых объектов. Для каждого объекта из `world_state.placed_instances` создаётся элемент `<body>` с указанием позиции, ориентации, геометрии и физических параметров.

**Шаг 5.** Вычисление массы объектов по формуле:

```
mass = volume × density
где volume = width × height × depth
```

**Шаг 6.** Применение физических параметров:
- `is_static = True` → отсутствие элемента `<freejoint>`
- `is_static = False` → наличие элемента `<freejoint>`

**Шаг 7.** Запись XML в файл `.cache/worlds/scene_latest.xml`.

## 9. КЛЮЧЕВЫЕ ОСОБЕННОСТИ И ПРИНЦИПЫ РАБОТЫ АЛГОРИТМА

### 9.1. Гибридный подход

Алгоритм реализует гибридный подход, сочетающий возможности больших языковых моделей и детерминированных вычислений:
- **БЯМ** отвечает за семантику, пространственные отношения и общую композицию сцены
- **Программный код** выполняет точные геометрические вычисления, валидацию и обнаружение коллизий

### 9.2. Детерминированный расчёт критических параметров

Z-координата всех объектов вычисляется исключительно программным кодом, независимо от ответа БЯМ. Это обеспечивает физическую корректность размещения и предотвращает ошибки типа "объект висит в воздухе" или "объект проваливается сквозь поверхность".

### 9.3. Каскад резервных механизмов

На каждом этапе алгоритма предусмотрены fallback-механизмы, обеспечивающие отказоустойчивость системы.

### Таблица 7. Резервные механизмы алгоритма

| Этап | Основной механизм | Резервный механизм |
|------|-------------------|-------------------|
| Построение графа | 3 попытки БЯМ с обратной связью | Эвристический построитель |
| Подбор моделей | Ранжирование + БЯМ | Словарь синонимов → RuntimeError |
| Масштабирование | 3 LLM запроса + агрегация | RuntimeError (fallback-таблица УДАЛЕНА) |
| Классификация физики | LLM | Volume Guard → RuntimeError (heuristic УДАЛЁН) |
| Размещение одиночного объекта | 6 попыток БЯМ | Исключение RuntimeError |
| Размещение батча | 5 попыток батчем | Последовательное размещение по одному (8 попыток каждый) |
| Размещение нескольких корней | БЯМ с контекстом потомков | Равномерная сетка |

### 9.4. Валидация на каждом шаге

Система выполняет многоуровневую валидацию:
- **Границы помещения:** |x|, |y| ≤ room_half_size × 1.1
- **Проекция родителя:** для типов on_surface, stacked_on, in
- **Минимальный просвет:** между экземплярами в батче
- **Дополнительная LLM-валидация:** проверка коллизий и согласованности

### 9.5. Топологическая сортировка

Применяется на двух уровнях:
- **Между якорями (уровень 0)** — определяет порядок размещения корневых объектов
- **Внутри групп потомков (по полю depends_on)** — обеспечивает правильную последовательность размещения зависимых объектов

### 9.6. Специальные режимы

- **N:K расщепление** — равномерное распределение потомков между родителями
- **Многослойная упаковка** — для контейнеров типа "in"
- **Координированное размещение** — для малых групп разнотипных сиблингов

## 10. ТОЧКИ ОТКАЗА БЕЗ FALLBACK

Система имеет три критические точки, где при неудаче LLM выбрасывается RuntimeError:

1. **Model Selection (Stage 1):** Если LLM не смог выбрать модель из кандидатов после disambiguation
2. **Model Scaling (Stage 2):** Если LLM не вернул размеры после 3 попыток с разными параметрами
3. **Physics Classification (Stage 2.5):** Если LLM не вернул решение static/dynamic для объекта

Эти изменения усиливают зависимость от качества работы LLM и исключают эвристические fallback-механизмы, которые могли давать неточные результаты.

## 12. ЗАКЛЮЧЕНИЕ

Разработанный алгоритм реализует последовательный конвейер обработки, где каждая стадия преобразует данные и передаёт их следующей. Ключевые принципы работы:

1. **Разделение ответственности:** БЯМ для семантики, код для геометрии
2. **Отказоустойчивость:** множественные fallback-механизмы на большинстве этапов
3. **Критические точки:** три этапа без fallback (model selection, scaling, physics) для обеспечения качества
4. **Валидация:** проверки на каждом шаге обработки
5. **Детерминизм:** критические параметры (Z-координата) вычисляются кодом
6. **Масштабируемость:** батч-обработка и иерархическая декомпозиция

Результат работы алгоритма — физически правдоподобная 3D-сцена в формате MuJoCo, готовая для симуляции и использования в задачах робототехники и машинного обучения.
